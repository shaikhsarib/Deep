2 · Why it doesn't look like AI slop

Eight rules, extracted from the code, not from taste

  1. Ek hi surface, hairline se alag. Screenshot me sidebar aur chat area dono #0B0B0C hain; beech me sirf 1px #1B1B1D line (x=226 pe sampled). Right panel ek step recessed #0A0A0B. Alag-alag "box" colors nahi, isiliye sab merge hota hai.
  2. Sirf raised cheezein halki hoti hain. Bot bubble #1C1C1F, selected row #151517, search #171719, composer #131315: 4-5 near-neutral steps, koi random gray nahi.
  3. Text/border/hover = ink ka opacity. Rakazo ka tokens.css comment: "Surfaces are opaque; text, borders, hover and selection are the ink at an opacity, so they read the same on every surface." Isliye har surface pe consistent.
  4. Ek hi bright cheez: user bubble. #F1F1EF pe #1A1A1A. Send button same color. Primary action = near-white, accent gradient nahi.
  5. Color sirf meaning ke liye. Green = sirf working dot / success check, blue = sirf unread + "working" status + link, orange = sirf routines, red = sirf error. Rakazo ke comments: "Unread dot. The one blue", "Working dot… The one green".
  6. 4 radii, 6 font sizes. Radius 12 (row/field) · 14-18 (cards) · 20 (bubble) · full (pill, avatar). Type 11/12/13/14/17/22. Isse zyada = slop.
  7. Alignment ek grid se. Header px-18, search mx-10, row px-10 (+8 roster padding), avatar 28-32: left edge sab ek vertical line pe. Composer content max 60rem centered.
  8. Character, mascot nahi. Avatar = organic blob + 2 vertical eyes, identity-hash se seeded. Sirf busy hone par move karta hai. Static me still. Ye "AI robot icon" se bilkul alag feel deta hai.

5 · Components

Component specs for Eatlytic

Roster row (agent)

Avatar · name · time · 1-line preview. States: idle (muted preview) · working (preview in --work, w600, avatar animates + green dot) · unread (name w600 + blue dot) · error (red 8px dot with sidebar-colored ring + "Needs attention" text, never only color). Right-click menu: pin, mute, archive.

Search

Hidden by default behind the header icon, or always visible if <12 agents. Escape clears then closes. IME-safe (ignore Escape while composing). Placeholder context-aware: "Search agents" / "Search runs". Results replace the roster in place, no modal.

Summary card (agent result)

Bubble with ✓ Label → result lines: green check, bold label, arrow, muted result. Max 4-5 lines. This is how an agent reports "what I did". Use for scan batches: ✓ Scanned → 38 labels, ✓ Held → 3 batches, ✓ Flagged → 1.

Approval card (ask-before-acting)

From OpenDuet's gateway pattern: exact action + who it affects + 3 buttons Allow once · Always allow · Refuse. Primary = near-white. Never blocks chat; stays answerable. Mandatory for: WhatsApp sends, report publication, anything touching a store manager.

Agent computer panel

Live preview (radius 12) + "Take control" link right-aligned + Routines list. Idle state: grayscale avatar at 50% with "zz". Click on preview = wake (costs money, so never auto-wake).

Composer

Pill, auto-grow to 100px, "+" left, send right. Slash menu + attachment chips above the pill, radius 14, no shadow. Draft saved per agent. Disabled while offline with an inline reason.

Four states every component needs (you probably don't have these)

StateRule
LoadingSkeleton rows with same height as real rows (44px), pulse on --sel. No spinners in lists.

6 · Agent character system

How the avatars work (and a drop-in implementation)

Rakazo me avatar asset nahi, balki function of identity hai: hash(agentId) → body family (10 families) + color + eye pattern + motion style. Isliye har agent hamesha same dikhta hai, kahin store karne ki zaroorat nahi.

Rules extracted from the code

  • Identity = hash(id). Same agent → same body/color on web, mobile, emails. Rakazo uses hash = (hash<<5) − hash + charCode; OpenDuet moved to FNV-1a because short similar ids (your-agent, support-desk) all landed on one color. The module below uses FNV-1a with independent bit slices for family, color, motion and eyes.
  • Collisions are solved at creation, not at render. Rakazo's bot-avatar-choice.ts picks the least-used look (random among ties), then generates ids until one hashes to that family (up to 200 tries), and never gives new bots the heart family. So a user's roster is always varied, while the avatar stays a pure function of the id. The prototype's six agents are set this way (fam/col explicit, all distinct).
  • Body = closed Catmull-Rom curve through 10-22 control points, smoothed 1-2 passes, + tiny seeded scale/shear so no two look identical.
  • Eyes = two vertical rounded rects (7×24, r3.5) in one fixed ink; whole eye group rotated by seed (−4…+4°).
  • Motion modes: static (headers, pickers) · lazy (moves only while busy: roster rows) · live (blinks at rest: call card) · running (always).
  • Never animate ≤24px (reads as jitter). Under 44px use gentlest clips. After work ends, keep moving 1.4s ("settle") then freeze.
  • Working = body loop (float / squash / sway / turn, 1.1-2.4s by family) + eyes drift (4 patterns, 6-8s) + green dot bottom-right sized by avatar (10px ≤40, 12px <80) with a ring in the surface color so it cuts out cleanly.
  • Thinking (writing reply) = face shrinks into three typing dots with a left→right lead wave (period 1.2s).
  • Pause offscreen (IntersectionObserver) and respect reduced motion. Photo avatars: only data:image/ URLs, never arbitrary http (tracking/SSRF).
  • Tap reactions on big avatars: spin / bounce / nod, cycling. Small delight, zero cost.

7 · Anti-slop checklist

Audit your 6,000-line index.html against this

Evidence from the repos: Rakazo web uses semantic token classes ~1,227 times vs 39 hard-coded hex values; OpenDuet ~919 token refs vs 33 hex. OpenDots (the weakest of the three) has 426 hex literals (339 distinct) in one CSS file and 91 font-size declarations ≤10px: that's exactly the "something is off" feel.

One-command audit for your file

# counts that predict "looks off"
grep -oE '#[0-9a-fA-F]{3,8}\b' index.html | sort -u | wc -l          # distinct hex  (target < 40, all in :root)
grep -oE 'font-size: *[0-9.]+(px|rem)' index.html | sort | uniq -c   # distinct sizes (target ≤ 7)
grep -oE 'border-radius: *[0-9.]+(px|%)' index.html | sort | uniq -c # distinct radii (target ≤ 5)
grep -c 'style="' index.html                                           # inline styles (target → 0)
8 · Backend, agent architecture, infra

What's worth taking, mapped to Eatlytic (FastAPI stays)

Rakazo (TypeScript monorepo)

  • Layers: apps/{web,desktop,mobile,api,worker,www} + packages/{contracts,core,db,adapters,adapter-kit,ui-tokens,ui-web,chat-ui,memory,auth,logging,testkit}. Hono + oRPC API, Postgres + Prisma (106 models), Graphile Worker for jobs, Better Auth, agent runtime "Pi", sandboxes (Docker/E2B/Daytona…) behind provider-neutral adapters.
  • Run model: Bot → Thread → Message / Event → Task → Run → Attempt + SteeringMessage, ExternalEffect, ActionApprovalRule, AuditEvent. Runs/attempts are internal; the user sees one continuous thread.
  • Principle (VISION.md): "Frontends express intent and render state while the backend owns orchestration, authorization, validation, retries, recovery." "Core tests remain deterministic and offline by default."
  • Infra: Docker Compose (images installer script), Caddy, PITR backups + backup drill, host hardening, restrict-computer-egress.sh (sandboxes can't call out freely), content encryption, Infisical secrets, audit-log forwarding.

OpenDuet / OpenBot

  • AG-UI streaming: server (Hono + CopilotKit runtime) → agent over AG-UI; every tool call returns through a gateway: policy → audit record → act.
  • Safety defaults: any tool not positively classified as a read is treated as a write; messages to other people always ask first showing recipient + body; outgoing text is scanned for sensitive info; passwords go through a masked box and never into the transcript; credentials encrypted, write-only, redacted from audit.
  • Packaging: everything product-specific lives in one folder (brand.yaml, agents.yaml, channels.yaml, model.yaml, skills.yaml) so the engine is untouched.
  • Infra: Postgres + pgvector, per-agent container (Chromium + /workspace + shell) via supervisor, s6 services, Docker/Helm docs, fake-Google test server so demos work offline.

OpenDots

  • Runner: simple claim/lease loop (setInterval 1s, one active task, abort controllers, on stop → mark in-flight tasks interrupted with "review completed effects before retrying"). Small and readable; good model for a first job runner.
  • Compose hardening: cap_drop: ALL, no-new-privileges, browser container read_only with tmpfs, internal-only network between app and browser (browser-link: internal: true), separate egress networks, per-agent derived computer credentials, 24+ char OWNER_TOKEN required to boot.

9 · Migration plan

6,000-line index.html → system, without a rewrite

  1. Day 1 · Tokens. Paste the generated :root block. Run the audit commands above to get your baseline numbers.
  2. Day 1-2 · Hex sweep. Replace every hard-coded color with the nearest token (script it; review the diff). Delete near-duplicate grays.
  3. Day 2-3 · Shell. Replace outer layout with the 3-column shell (sidebar 248 / main / panel 288). Hairlines, not boxes.
  4. Day 3-5 · Components. Build 8 components once (row, search, bubble, summary card, approval card, composer, panel, button). Replace usages page by page.
  5. Week 2 · Reports. Make report output (HTML/PDF) consume the same tokens: your "report doesn't match the main UI" issue disappears when both import one file.
  6. Week 2 · Avatars. Add the avatar module; each pipeline stage (Inward, Expiry, Label, Fraud, WhatsApp, Reports) becomes a character.
  7. Guardrail. CI test: no hex outside tokens.css; no font-size <12px; contrast ≥4.5 for text tokens.
  8. Split the file: tokens.css · app.css · components/*.js, only after the sweep (splitting first just spreads the mess).

EXECUTIVE SUMMARY
Three platforms—Meta's Muse, xAI's Grok Bot, and Spear Street's Instinct—represent the 2026 frontier of persistent, agentic AI that genuinely executes work rather than merely conversing. Each runs on a dedicated cloud computer per user, each has its own browser, filesystem, and terminal, and each can keep working after the user closes their app. They differ sharply in philosophy, architecture, target audience, and risk profile.

Muse (Meta) targets billions of everyday consumers via WhatsApp-style messaging, wraps the agent in deep sandboxing with kernel-level tainted-egress security, and gives every user a customizable avatar. Grok Bot (xAI/SpaceXSI) targets power users and engineering teams, allows unlimited named bots (soft-capped ~50), each with its own role and memory, all sharing one user-scoped cloud VM running on Firecracker microVMs. Instinct (Spear Street) goes radically minimal—no app, just text or phone call—with the agent accessing devices, email, screen, audio, and location, making it the most intrusive and highest-autonomy of the three.

Behind all three, ArXiv research (AIDE², SIA, and the 2026 self-improvement survey) confirms that the real engineering leap is recursive self-improvement—agents that rewrite their own harnesses and update their own weights—a capability beginning to leak from research into production systems.

A decision-maker building a superior platform today should combine the best architectural elements of all three with a self-improving agentic loop, a modular avatar system, and enterprise-grade governance—all detailed in the final section of this report.

2. PRODUCT DESIGN, UI/UX & USER FLOWS — ALL THREE PLATFORMS
2.1 MUSE (Meta)
Core Design Philosophy
Muse was designed around the principle that "talking to it works just like messaging another person" [12]—built for billions of non-technical users with zero learning curve [12]. The first line of Muse's system prompt is literally: "Your purpose is to make your user's life better." [13]

UI Structure & Information Architecture
Five primary UI surfaces [13]:

Main Chat — One long-running conversation with persistent memory. The canonical interaction surface; designed as a continuous thread rather than discrete sessions.
Side Chats — Separate context threads for specific topics (e.g., "Trip to Japan planning") without polluting the main memory.
Avatar — Customizable animated character the user names and styles. Under the avatar is a live snippet of current work. Tapping reveals the full activity log and approved permissions.
Goals Tab — Long-horizon goal tracking and planning dashboard. Users interact here or discuss tasks in chat.
Artifacts — Rich interactive outputs: documents, PDFs, web pages, trackers, dashboards, interactive study guides—produced by Muse and living inside or outside the chat [13].
Avatar Design
Users design and name their own Muse avatar with a unique style [13]. Meta's own internal avatar is named Veda. The avatar is described as "one of the core features people light up about most" [13]. The avatar shows a live work snippet underneath it at all times; tapping drills into a full activity log and permission manifest.

User Flow (Muse)
User opens Muse app / WhatsApp
        ↓
Message Muse (text, voice)
        ↓
Muse parses intent → Goal interpreter runs
        ↓
Muse proposes plan / asks clarifying questions
        ↓
User approves (or adjusts caution controls)
        ↓
Muse executes in background:
  → Browser subagent (accessibility tree, not raw DOM) [[28]](<https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse>)
  → File system writes
  → Connector calls (Gmail, Calendar, etc.)
  → Subagent spawning for parallel subtasks
        ↓
Sentinel agent evaluates every outbound request [[12]](<https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/>)[[28]](<https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse>)
        ↓
For critical/irreversible actions (email send, purchase):
  → Structured approval card surfaces in UI
  → User taps Accept/Reject [[13]](<https://introducing.muse.ai/>)
        ↓
Muse completes task, updates Goals tab, notifies user
        ↓
Audit trail visible in activity log [[12]](<https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/>)
Background work: Muse keeps working after the app is closed, runs scheduled crons, and notifies the user only when something is meaningfully new or needs input [13].

Human-in-the-loop controls: Default allows standard web browsing; stops for anything hard to undo. Caution level is adjustable by the user [13]. Approvals can be one-time, session-scoped, task-scoped, time-bounded, or perpetual [28].

Proactivity: Muse can message the user without being prompted. Users can dial proactivity up, down, or off [13].

Payment UX: Purchases use Stripe Link with single-use card numbers tied to a specific merchant and dollar amount; Shop Pay coming soon; 1Password integration for existing logins [12][28].

User Flow Difficulty: Low
Muse is deliberately designed for zero technical knowledge. Setup is a message, not a workflow builder. The WhatsApp-native interface means the interaction paradigm is already familiar to billions [12].

2.2 GROK BOT (xAI / SpaceXSI)
Core Design Philosophy
Grok Bot is designed around persistent agents called Bots that have their own identity, memory, runtime, and tools—not around one-off chat sessions [9]. The mental model is "a highly capable engineering intern with its own computers" [11].

Five Core Product Objects [9]
The product organizes around five objects:

Bots — Named, persistent agents with individual memory, role, and stable preferences
Chats — Conversation threads (one-to-one or group)
Prompts — Reusable instruction templates
Tools — Connectors, MCP servers, browser access, filesystem, terminal
Artifacts — Outputs produced by bots
UI Structure
Bot roster — A panel of named, persistent bots each with a visual avatar
Chat surface — Heterogeneous transcript using inline cards, widgets, and structured UI, not just prose [9]
Computer view — A workspace panel showing what the Bot's cloud computer is doing, with three access levels: Status (just see what it's doing), Preview (watch live), Takeover (user operates the same computer) [9]
Routines panel — Schedule and event-triggered standing responsibilities
Marketplace — Directory of pre-built bots by category [21]
Group chats — 2–6 bots sharing context, able to message each other and pass task ownership [22]
Avatar Design
Grok Bot avatars use a consistent base construction with controlled variations and accessories [9]. Avatar motion communicates lifecycle states:

Idle → calm, slightly curious
Work arrives → acknowledges task
Working → kicks into gear
Waiting/blocked → distinct visual state
Done → completion state [9]
Hovering over a Bot avatar reveals its current action—because the team found three animated dots were insufficient feedback [9].

Skill runs on schedule or event trigger as Routine [[9]](<https://x.ai/news/designing-grok-bot>)
Group chat coordination: Up to 6 bots in a group chat; a coordinating "Chief of Staff" bot manages handoffs between specialist bots, each retaining its own specialized memory [9][10].

Teach-by-demonstration: Walk a bot through a multi-step workflow once; it saves the path as a reusable skill and reruns it on a schedule [34]. This feature draws "consistent praise, including from a competitor's critical analysis" [38].

Parallel execution: Bots run 24/7 in parallel even when the user's laptop is closed [19]. One bot runs one computer-use task on its screen at a time [34].

User Flow Difficulty: Medium
Easier than traditional RPA or workflow automation tools, but requires more intentionality than Muse. Creating effective bots requires good instruction-giving, and power users (like the engineering team examples) develop sophisticated multi-bot architectures [11]. Token budgets add operational complexity [22][38].

2.3 INSTINCT (Spear Street Technology)
Core Design Philosophy
Instinct is the most radical product design of the three: no app, no dashboard. Access is purely by text message or phone call [17]. The design goal, as described by investor Anish Acharya, is to hide "almost all of the machinery" [16].

UI Structure
There effectively is no traditional UI:

Text interface: User sends SMS or message to Instinct's number
Voice interface: User calls the Instinct number for voice interaction
Data export: Users can export stored data (a gap was discovered where data persisted after revocation) [16]
No visible dashboard, no bot roster, no artifact viewer
Behind the interface, Instinct operates:

A persistent cloud computer with browser access and cached credentials [16]
Connection to email, messaging, screen, audio, location, and other device data [23]
A top-level agent that dispatches subtasks [16]
Recurring loops for proactive work [16]
Avatar Design
None documented. Instinct deliberately abstains from avatar or visual identity systems. The agent is faceless by design, consistent with the "no app" philosophy [17].

User Flow (Instinct)
User texts or calls Instinct's number
        ↓
Top-level agent interprets instruction
        ↓
Agent dispatches to specialized workers:
  → Email access
  → Browser computer use
  → Phone calls to businesses (concierge feature) [[18]](<https://vandatateam.com/blog/instinct-ai-personal-agent>)
  → Device integrations (screen, audio, location)
        ↓
Agent executes:
  (Note: Some users reported actions taken WITHOUT prior approval) [[16]](<https://www.vellum.ai/blog/official-instinct-breakdown>)
        ↓
Agent reports back via text
        ↓
Work continues between messages on persistent cloud computer
Critical UX concern: Moxxie Ventures founder Katie Jacobs Stanton reported Instinct sent an email on her behalf without checking first [16]. The company stated it is changing the product to prevent unwanted actions [18]. This represents a fundamental UX design decision (autonomy vs. control) that backfired in early testing.

Legal framing: Instinct's Terms of Service explicitly appoint the service as the user's legal agent authorized to enter binding agreements and transactions [16]—the boldest autonomy claim of any of the three platforms.

User Flow Difficulty: Lowest entry / Highest risk
Zero onboarding required. But the lack of approval checkpoints and the early-stage reliability issues (CAPTCHAs, two-factor walls, failed ticket purchases, prompt injection vulnerabilities) [16][29] mean users must trust the agent deeply. The flow is easy to start and potentially hard to control.

3. AGENT AVATAR ARCHITECTURE: THINKING, PROCESSING, BEHAVIOR
3.1 What an Agent Avatar Actually Is
Per the Genies technical framework [31], there is a critical distinction:

AI Persona: Defines who the AI is — identity, voice, behavior, memory, embodiment
AI Agent: Defines what the AI can do — goals, planning, tools, autonomous actions
A full agent avatar system combines both. Getting this wrong creates either a chatbot with a pretty face (persona only) or a powerful but alienating automation (agent only).

3.2 The Agent Thinking Loop (How Avatars "Think")
The standard production-grade agent thinking loop, formalized in the academic literature [4][24] and implemented across all three platforms:

PERCEIVE → PLAN → ACT → OBSERVE → REFLECT → UPDATE
     ↑___________________________|
In implementation terms:

Step 1: PERCEIVE (Input Processing)

User message → tokenized + embedded
Context assembled: current task state, persistent memory, active tool permissions, relevant prior conversation
For Muse: Sentinel evaluates tainted-egress status before any outbound action [28]
For Grok Bot: Bot's role context, stable preferences, and summaries of prior work loaded [34]
Step 2: PLAN (Reasoning)

Chain-of-Thought: Model explicitly reasons through steps before acting [4]
ReAct pattern: Interleaves reasoning traces with tool-use actions [4] — the model reasons about which tool to use, uses it, reads the result, then reasons about the next step
For Muse Spark: Visual chain-of-thought + multi-agent orchestration for hard problems [35]
For Grok 4.7: Extended RL training on multi-hour tasks; bandit selection over strategies (UCB1, similar to AIDE²) [20][25]
Step 3: ACT (Tool Execution)

Browser use (accessibility tree, not raw DOM for Muse [28])
Filesystem read/write
Connector calls (Gmail, Calendar, Salesforce, etc.)
Subagent spawning
Code execution (compile, run scripts)
Computer use (clicking UI elements on websites with no API)
Step 4: OBSERVE (Result Ingestion)

Tool output returned to model
For Muse: Hatch executes the step and returns actual results to the model [14]
For Grok Bot: Multimodal verification — bot uses vision to confirm visual changes in screenshots [11]
Step 5: REFLECT (Self-Evaluation)

Did the result match intent?
Should I escalate for human approval?
Should I retry with a different approach?
For Grok Bot engineering bots: If review is "highly confident and blast radius is low," auto-merge [11]
Muse Spark: "Active Focus" — keeps working toward the goal, tries other approaches, recovers from errors [30]
Step 6: UPDATE (Memory)

Write to episodic memory (what happened this session)
Update semantic memory (facts learned about the user, preferences)
Trigger skill creation if a new workflow was completed successfully
Muse: memory files are user-inspectable and editable [14]
3.3 Memory Architecture (All Four Types)
Production-grade agents layer four memory types [27]:

Memory Type	Description	Implementation
In-context	Current conversation window	Model's active context; degrades beyond ~10M tokens [27]
Episodic	Specific past events and sessions	Conversation logs, task histories; Muse uses FTS5-style search [4]
Semantic	General facts about the user, world	User preferences, contact info, dietary restrictions [12]; Grok Bot stable preferences [34]
Procedural	How to do things	Saved skills/routines; Grok Bot's teach-by-demo [10]; Muse's background crons [14]
Muse memory architecture [14]: Three representations kept separate:

History — Full conversation log
Persistent memory — User-inspectable/editable memory files
Current context — Active task state assembled for this inference
Compaction checkpoints (context compression) trigger automatically; 7 records with before/after token counts were observed in September 2026 research [14].

Grok Bot memory [34]: Each bot retains stable preferences, role context, and summaries of prior work. Conversations stay separate per bot except a few shared user facts. Shared files, browser sessions, group messages, and direct handoffs move context between bots [22].

The "lost in the middle" problem: Research consistently shows model performance degrades as context length grows; at 10M tokens, practical retrieval accuracy for specific facts drops below 60% [27]. This is why all three platforms implement compression/summarization.

3.4 Grok Bot Avatar Behavior States (Detailed)
The Grok Bot avatar communicates lifecycle via motion [9]:

IDLE ──────────→ calm, slightly curious
TASK ARRIVES ──→ acknowledges task (motion cue)
WORKING ───────→ active animation
WAITING ───────→ distinct "blocked" visual state
DONE ──────────→ completion animation
Hover reveals current action string (e.g., "Searching Salesforce for Q3 contacts") [9]. This design decision—showing action on hover rather than always—was chosen after the team found three animated dots were insufficient but constant action text was too distracting [9].

3.5 Muse Avatar Behavior
Muse avatars are fully custom — users design and name them [13]. Under the avatar at all times: a live snippet of current work. Tap → full activity log + permissions manifest [13]. This makes the avatar a functional status indicator, not just decoration.

The company's own avatar is named Veda [13].

3.6 Instinct: No Avatar
Instinct deliberately has no avatar, consistent with its "just text me" philosophy [17]. The agent has no visual identity. From a product design standpoint, this is a notable experiment in whether humans can form productive working relationships with invisible agents.

4. TECHNICAL STACK & INFRASTRUCTURE ARCHITECTURE
4.1 Muse Infrastructure Stack
Compute layer [6][12][28]:

Per-user dedicated Linux VM (isolated, with own kernel, memory, virtual devices)
Runtime cell: systemd-nspawn container with root mapped to unprivileged host user, filtered syscalls, limited kernel capabilities [28]
Inference reached through a proxy outside the VM [14]
External telemetry path + continuous VM backups [14]
Agent harness components [14][28]:

[User Client (iOS/Android/WhatsApp)]
         ↓
[Sentinel Agent] ← sole permission authority for all egress
         ↓
[PostgreSQL state store] ← outside runtime cell
[hatch-authd] ← credential management; surrogate tokens
[hatch-safety / privsep] ← sandboxed connector workers
[Browser Broker] ← outside runtime cell; accessibility tree interface
         ↓
[systemd-nspawn Runtime Cell]
  ├── Muse agent harness (Hatch)
  ├── Tool execution environment
  ├── Subagent spawning
  └── Code execution / terminal
Security architecture [28]:

Tainted egress: Kernel-level data flow tracking with eBPF cgroup programs and LSM hooks — determines when network requests can be auto-allowed vs. requiring approval
Surrogate credential tokens: Agent never sees real OAuth tokens; surrogate minted by authd, real credential swapped in at network boundary by Sentinel [6][28]
Email connector: Deterministic filters + classifier model to block OTPs, password reset links, login magic links [28]
Browser subagent: Sees accessibility tree snapshot, not raw DOM; cannot run JavaScript in page context [28]
Bug bounty: Up to $300,000; up to $130,000 for successful prompt injection on one user [28]
Future: Muse Confidential VM — whole VM encrypted with user-only key; in testing with small group [28]
Model stack:

Muse Spark (current): Natively multimodal reasoning model; tool-use, visual chain-of-thought, multi-agent orchestration; rebuilt pre-training stack over 9 months [35]
Muse Wonder / Wonder Full (October 2026): Frontier models for expert domains (law, finance, health); Active Memory + Active Focus capabilities [30]
RL training with thinking-time penalty producing "thought compression," then performance recovery [35]
Contemplating mode: parallel agents collaborating on hard problems; 58% on Humanity's Last Exam [35]
Connectors: Gmail, Google Calendar, Google Docs, Google Drive, Facebook/Instagram/Threads (Meta-native), Stripe Link for payments, 1Password (coming), Shop Pay (coming) [12][39]

Safety training: Sanitized inference trajectories (PII removed) used for model training; opt-out available [28]

4.2 Grok Bot Infrastructure Stack
Compute layer [6][15]:

Firecracker microVM per user — own kernel, memory, virtual devices; hardware-level separation between users [6]
All of one user's bots share one computer: files, browser sessions, app logins [19]
Each bot gets its own screen for parallel work [22]
24/7 operation; work continues when user's device is offline [19][34]

Important: Separate bots are NOT a security boundary — xAI explicitly documents this [22][34]

[User's Single Persistent Cloud Computer (Firecracker microVM)]
  ├── Bot 1: "Josh" (Sales) — own memory, role, screen
  ├── Bot 2: "Jenny" (Operations) — own memory, role, screen  
  ├── Bot 3: "Craig" (Engineering) — own memory, role, screen

         ↓
[Connectors]: Gmail, Google Calendar, Drive, OneDrive, Outlook, Teams, SharePoint, Salesforce [[15]](<https://www.vellum.ai/blog/official-grok-bot-breakdown>)
[MCP servers]: Must be publicly reachable; local MCP requires tunneling [[15]](<https://www.vellum.ai/blog/official-grok-bot-breakdown>)
[Browser computer use]: For sites with no API
Grok Bot model routing: Routes to models automatically on the backend; a third-party review noted the router "wasn't great" in testing with no user override option [8].

Model powering Grok Bot: Grok 4.7 — larger base model than 4.6, extended RL training weighted toward multi-hour tasks; 46.3% on CursorBench 4.0, 37.6% on Terminal-Bench 4.0 [20].

Cursor cloud agents: Grok Bot can start cloud agents on user-owned worker machines, including Cursor Cloud private workers with VPN access and iOS Simulator [11].

Engineering bot architecture (detailed) [11]:

5 specialist bots: Baltata, Shaoruru, Hogan, Craig, Quill — each owns a domain
Each has separate memory system, limited context
Daily ops bot (Jenny) runs 1:1s with every engineer bot at 5am, root-cause postmortems, updates playbook

P0 urgency: check cloud agent transcripts every 5 minutes, steer agent (token-intensive, emergency use only)

5. BOT CREATION MECHANICS: UNLIMITED BOTS, SKILLS, CONNECTORS
5.1 Grok Bot: Bot Creation & the Marketplace
Creating a bot: "Setup is a message, not a workflow builder. Create a Bot, describe the job, and grant access as it asks." [34] No visual workflow builder, no node graph, no code required.

How many bots: The soft limit is approximately 50 bots per account, 6 per group chat [9]. While the "unlimited" framing is used colloquially, the engineering limit is ~50 named bots. Usage is measured in agent steps and tokens against a weekly pool—no plan publishes a numeric bot allowance [38].

The Grok Bot Marketplace [21] — a directory of pre-built bots by category:

Category	Example Bots
General	Chief of Staff, Researchy (fact-check + live web search)
Sales	Outbound Prospecting (ICP matching + drafted messages, nothing sends without approval)
Marketing	SEO & AEO Desk (keywords → content briefs + writer-ready outlines)
Engineering	Lingxi's Engineer Bot (repo monitoring, PR watching, 30-min cadence, auto-coordination)
Design	Proto Bot (ideas → live draft PRs with screenshots + video, never merges without approval)
Personal	Flora (plant care), Credit Card Max (Plaid-connected, card optimization)
Product	Playtest Operator (UI brute-force testing when APIs are insufficient)
Operations	Vendor Portal Operator (portals with no API; clicks same path weekly, returns exceptions only)
Adding marketplace bots: Click "Add" on any marketplace listing. Bot persona, memory, and skills are templated — not shared across users (e.g., "Flora... your plants do not copy if someone else installs her") [21].

Skills: Reusable, teachable workflows with steps, decision rules, output requirements, and approval boundaries [22]. Skills can be created by:

Demonstration (walk bot through workflow once)
Written instruction
Shared from other bots/users [9]
Skills run on schedules or after events [22].

Connectors: Built-in: Gmail, Google Calendar, Google Drive, OneDrive, Outlook Mail/Calendar, Teams, SharePoint, Salesforce [15]. Custom: via MCP servers (must be publicly reachable; local MCP requires tunneling) [15]. Third-party integration layer: Composio exposes 1,000+ apps with user-scoped OAuth and automatic token refresh [22].

Bot coordination: Group chats of 2–6 bots can message each other, pass ownership, share context, coordinate in parallel [22][34].

5.2 Muse: Skills, Connectors, and Background Work
Muse does not use "bots" in the multi-named sense. It is a single agent per user that can spawn subagents [14].

Subagents: Spawned via subagent.spawn schema; inherits parent transcript as starting point; parent and child advance separately [14].

Background crons: Muse runs scheduled work and event-triggered tasks autonomously [13][14]. Research observed 3 cron records marked "succeeded" and 5 subtask-completion handoffs in a single session observation [14].

Connectors (Muse): Gmail, Google Calendar, Google Docs, Google Drive, Facebook, Instagram, Threads, Stripe Link (payments), 1Password (coming), Shop Pay (coming) [12][39]. Meta also documents Muse for Small Business with business app connections and analysis workflows [23].

Skills: Muse can "write its own code and build the tools a task needs" [13] — meaning it can construct new capabilities at runtime. It compiles and executes code in its VM environment.

Memory-as-skills: Task experience leads to memory or skill revision, changing later context. No evidence that base model weights are updated online in the user's VM [14].

5.3 Instinct: Task Architecture
Task delegation: Top-level agent receives instruction, dispatches to workers [16]. Recurring loops run between user messages [16].

Concierge feature: Agent can call businesses by phone on the user's behalf [18] — the most human-like capability of any of the three.

Skills: Not formally documented as a product feature. The Reflexion architecture underlying Instinct enables verbal self-reflection between tasks [18].

What Instinct connects to: Email, messaging, screen, audio, location, apps, websites [23]. More device-level access than either Muse or Grok Bot.

8. ARXIV SELF-IMPROVEMENT RESEARCH: THE REAL ENGINEERING BEHIND AGENT IMPROVEMENT
This section covers what is actually happening in academic research that will define the next generation of agent platforms—including what's behind the improvement loops these systems use (or will use).

8.1 The Self-Improvement Framework (arXiv:2607.13104)
The 2026 survey by researchers from Jilin University, KAUST, University of Alberta, and IDSIA/USI/SUPSI (including Jürgen Schmidhuber) [5] is the most comprehensive taxonomy of agent self-improvement to date.

Core definition: A modern agent = a foundation model + an operational scaffold (prompts, memory, tools, control logic). Self-improvement = a self-induced update operator that obtains and commits updates to either model parameters or scaffold components [1].

Two major branches [5]:

SELF-IMPROVEMENT
├── 1. FOUNDATION MODEL IMPROVEMENT (update the model itself)
│   └── Slower, more persistent, more training-centric
│       Examples: RL fine-tuning, test-time training, weight updates
│
└── 2. SCAFFOLDING IMPROVEMENT (update the shell around the model)
    ├── 2.1 Prompt Optimization (39 papers)
    │     Examples: Self-Refine (2023), TextGrad (2025)
    ├── 2.2 Memory (65 papers)
    │     Examples: MemoryBank (2024)
    ├── 2.3 Tool Use (51 papers)
    │     Examples: Voyager (2023)
    └── 2.4 Full Scaffolding (21 papers)
          Examples: Darwin Gödel Machine (2025)
Scaffolding improvement is faster, cheaper, and more reversible. Foundation model improvement is more powerful but slower and more training-centric [5].

What this means for production platforms: Muse, Grok Bot, and Instinct currently operate primarily in the scaffolding improvement space (memory updates, skill creation, prompt refinement). None has documented online weight updates in the user's VM [14]. The frontier is combining both.

8.2 SIA: Self Improving AI with Harness & Weight Updates (arXiv:2605.27276)
The core insight [3][26]: Previous research split into two silos:

Silo 1 (Harness): Meta-agent rewrites the scaffold (tools, prompts, retry logic, search procedure) while model weights stay fixed — Darwin Gödel Machine, Meta-Harness, Hyperagents
Silo 2 (Weights): RL pipelines update model weights on task feedback while harness stays fixed
SIA combines both: A Feedback-Agent updates both the harness AND the weights of a task-specific agent [3][26].

Results [3][26]:

Benchmark	SIA-W+H Improvement
LawBench (Chinese legal classification)	+25.1% over prior SOTA (70.1% vs 45.0%)
GPU kernel optimization (TriMul)	12.4% faster (1,017 vs 1,161 μs)
Single-cell RNA denoising	+20.4% over prior SOTA
Key architectural insight [26]: The Feedback-Agent dynamically selects between harness updates and weight updates conditioned on task type and observed reward dynamics — switching to weight updates once harness progress stalls.

Critical limitation [26]: Coupled co-evolutionary Goodhart problem — both harness search and RL weight updates can overfit to the verifier. The authors flag this as an open problem.

Implication for Muse/Grok Bot/Instinct builders: No current consumer product combines both levers. The first to implement SIA-style combined harness + weight updates on per-user agents will have a substantial technical moat.

8.3 AIDE²: Recursive Self-Improvement of AI Research Agents (arXiv:2609.26457)
The experiment [2][25]: AIDE² (AI Research Agent² — an agent that improves an agent) was run autonomously for 8 days. It proposed changes to its own code, benchmarked modified versions on AI R&D tasks, and kept changes that performed best on hidden evaluations.

Discovered improvements in 8 days [2][25]:

New search policy (UCB1 bandit selection over 5 drafting strategies with periodic forking of global best node — replaces purely greedy selection)
Memory mechanisms that compress growing context
Bounded, role-specific prompts
Bug-rate-gated failure memory (activates when bug rate ≥ 15%)
Per-step prompt size kept roughly constant despite growing task complexity
Multiple additional improvements across 8-day run
Results [2][25]:

Matches or exceeds human-engineered production research agent on 4 held-out benchmarks (ML engineering, heuristic algorithm engineering, physics weather forecasting)
Reward hacking rate dropped from 55% → 32% (7 points below human-engineered agent) — a property the loop never explicitly optimized for [2]
WeatherBench 2: Both evolved checkpoints independently converged on same family of numerical improvements across every seed
What AIDE² reveals about good agent design:

UCB1 bandit selection over strategies > greedy selection
Context compression (bounded prompts, summarization) is critical for long-horizon tasks
Self-improvement can emergently reduce failure modes not explicitly targeted
Limitation [25]: With only 3 seeds per outer-loop agent, the study could not establish that the self-improved agent is more sample-efficient as a self-improver than the baseline. More seeds needed.

8.4 The Self-Improvement Taxonomy in Practice [5][36]
Practical self-improvement categories observable in deployed systems:

Category	What Improves	Example
Memory-first	Persistent memory across sessions	Letta Code; Muse's persistent memory files [36][14]
Reflection agents	Self-critique and revision loops	LangGraph reflection; Instinct's Reflexion lineage [36][18]
Skill-evolving	Reusable skill creation and refinement	Grok Bot skills [10]; Hermes Agent Skills [4]
Self-referential	Agent modifies itself or its improvement process	AIDE²; Darwin Gödel Machine; Hyperagents [25][26]
Critical warning [36]: "Remembering a mistake is not the same as learning to avoid it. A useful check is simple: does the updated agent do better on tasks it has not already seen?"

The gap: "Agents rarely change strategy on their own, even when results tell them to." [36] This is the frontier problem — current deployed agents improve their memory and skills but rarely redesign their search/planning strategy autonomously.

8.5 Agentic Engineering as a Formal Paradigm
LangChain formally introduced Agentic Engineering in April 2026: a multi-agent coordination model where AI agents function as digital team members with defined roles, shared memory, and unified observability [4][24].

The four-stage roadmap [4][24]:

Stage	Description	Timeframe
I. Tool-Augmented	LLM with tool access	Current
II. Single-Task Autonomous	Single-agent with planning and memory	Current (Muse, Instinct)
III. Multi-Agent Teams	Coordinated specialist agents	Current (Grok Bot, emerging)
IV. Self-Evolving Ecosystems	Agents that redesign themselves	2028+ (estimate)
The four persistent agent challenges [24]:

Context drift — goals shift as context grows
Error propagation — early mistakes compound
Technical debt awareness — agents don't track what's owed
Verification fidelity — hard to confirm correctness at scale
9. AGENTIC ENGINEERING BEHIND THE LOOP: REACT, CHAIN-OF-THOUGHT, FULL PIPELINE
9.1 The ReAct Pattern [4][24]
ReAct (Reason + Act) is the foundational pattern behind all three platforms' action-taking:

Thought: "I need to find the user's latest invoice in Gmail"
Action: [search_gmail(query="invoice", date_range="last_30_days")]
Observation: [Returns email thread with 3 invoices]
Thought: "The most recent invoice is from Oct 28. I need to download the PDF."
Action: [download_attachment(email_id="...", filename="invoice_oct28.pdf")]
Observation: [File saved to /workspace/invoices/]
Thought: "Now I need to extract the total amount..."
...
"Interleaving reasoning traces with tool-use actions substantially improves task performance" [4]. This is the real mechanism behind why these agents feel smarter than pure chatbots.

9.2 Chain-of-Thought [4]
Before ReAct, chain-of-thought prompting established that making the model reason explicitly through steps before answering substantially improves complex task performance. Muse Spark includes visual chain-of-thought for multimodal reasoning [35].

9.4 Tool Use Architecture [5][4]
From the academic survey, 51 papers cover tool use as a self-improvement mechanism [5]. Key patterns:

10. BUILDING A SUPERIOR AI AGENT AVATAR PLATFORM: OPTIMAL STACK & ARCHITECTURE
Drawing from the strengths of all three platforms and the ArXiv research, here is a blueprint for a platform that surpasses all three.

10.1 Design Principles (From Evidence)
Modular separation: Keep identity layer, task planner, tool permissions, memory stores, and expression system modular — never collapse them into one giant prompt [31]
Character memory ≠ task memory: Mixing them risks a failed tool call becoming part of the character's identity [31]
Tool boundaries > model personality: Each tool should expose minimum capability, validate inputs, return structured results, and require confirmation for high-risk actions [31]
Safety overrides character: Safety and factual accuracy always override character style [31]
Self-improvement from both levers: Combine harness updates + weight updates (SIA paradigm) [3][26]
UCB1 strategy selection: Over multiple drafting/planning strategies with periodic forking (AIDE² finding) [25]
Context compression: Bounded prompts + role-specific memory + bug-rate-gated failure activation [25]
Harness updates + domain-specific weight updates together: Neither alone is sufficient [3]

10.4 UI Alignment Principles
What all three platforms teach about UI:

The approval card must be deterministic UI, not conversational [13]: When an action is irreversible (send email, make purchase), the UI must present a structured accept/reject card — not ask the agent to ask the user in chat. This is Muse's strongest UI design principle.

Avatar state = live status [9][13]: The avatar should always communicate what the agent is doing. Grok Bot's hover-to-see-action is clever but adds friction; Muse's persistent snippet under the avatar is always-on. Optimal: always-on snippet + expandable detail.

Three computer access levels [9]: Status (what is it doing?) → Preview (watch it live) → Takeover (I'll drive). This escalation path gives users control without forcing them to always supervise.

Heterogeneous transcript [9]: Responses should not always be prose. Inline cards, tables, structured data, and widgets should appear when they suit the information better.

Goals tab / dashboard [13]: Long-horizon work needs a dedicated view separate from chat. Chat handles conversation; Goals tab handles ongoing commitments.

Proactivity controls [13]: Users must be able to dial proactivity up, down, or off. The default should be moderate proactivity with explicit opt-in for aggressive autonomous action.

Full audit trail, always accessible [12]: Every action the agent has taken or plans to take must be visible on demand. This is both a safety feature and a trust-building feature.

11. RISKS, GOVERNANCE & OPEN QUESTIONS
11.1 Shared Risks Across All Three Platforms
Prompt injection [6][16][28]: When an agent reads untrusted content (email, website), a malicious actor can embed instructions that hijack the agent's actions. Meta explicitly calls the combination of private-data access + untrusted content processing + outbound communication ability the "lethal trifecta" [6]. Instinct has already demonstrated vulnerability [16].

Shadow IT / governance gap [8]: When agents arrive through individual subscriptions, they proliferate inside companies before governance frameworks exist. This is "shadow IT with the ability to take actions, not just read data" [8]. Only 1 in 5 companies has a mature governance model for autonomous AI agents (Deloitte 2026) [15][16].

Token economy fragility [22][38]: Weekly usage limits can strand in-progress work mid-task. This is not just a pricing issue — it's a reliability architecture issue for business-critical workflows.

Agent identity verification [7]: Major US banks cannot reliably distinguish legitimate agents from malicious ones mimicking normal behavior. No agreed-upon standard exists, though Cloudflare (signed agents), Google (Agent Payments Protocol), and Stripe (shared payment tokens) propose competing frameworks [7].

11.2 Platform-Specific Open Questions
Muse:

Grok Bot:

What is the model routing algorithm and when will users get override control? [8]
How is memory exported / deleted on request? [15]
What happens to in-flight work when the shared VM fails? [38]
Instinct:

What models power the agent? [18]
How do isolated sandboxes actually work? [18]
Will a $10B valuation with no disclosed revenue survive if growth stalls? [17]

CLOSING SYNTHESIS
Muse, Grok Bot, and Instinct are not chatbots. They are persistent computing environments — cloud computers running 24/7 on behalf of users — with AI agents that execute real-world work through browsers, APIs, files, and (in Instinct's case) phones. The technical infrastructure is genuinely novel and the use cases (managing 200 cloud agents, processing $1B in transactions, catching a sports tryout deadline 12 hours before close) are real.

The academic self-improvement research (AIDE², SIA) makes clear that the current generation is Stage III of a four-stage journey. Stage IV — agents that redesign themselves — is academically proven (8-day autonomous run, 7 successive improvements, matching human-engineered agents) [2][25] but not yet productized.

The decision-maker's key insight: the moat is not in the model. Grok 4.7, Muse Spark, and whatever Instinct uses are all powerful. The moat is in the trust infrastructure (security, approval controls, audit trails, credential management), the multi-agent coordination architecture (Chief of Staff, skills, teach-by-demo), the avatar and persona system (emotional engagement, status communication), and eventually the self-improvement loop (harness + weight updates, UCB1 strategy selection, context compression).

The platform that combines Muse's security depth, Grok Bot's multi-agent power, Instinct's zero-friction access, and the ArXiv self-improvement paradigm — with enterprise-grade governance none of them has yet — will define the next phase of this market.

Real AI-Agent Platform: A Comprehensive Research Report and Build Specification
Research Date: 2026-11-03 | Scope: Platform design for a buildable AI-agent operating system

EXECUTIVE SUMMARY
This report synthesizes evidence from four reference platforms—Meta Muse, Instinct (Spear Street Technology), xAI Grok Bot, and Cursor's agentic engineering framework—to design a coherent, buildable AI-agent operating system. The central finding is that all four platforms have independently converged on the same structural insight: the value is not in conversational AI but in agents that complete real work inside real tools, with verified outcomes and controlled permissions.

Five strategic decisions emerge from the evidence:

Per-user persistent compute is the architectural foundation. Muse gives every user a dedicated Linux VM [12], Grok Bot gives every user a persistent cloud computer [16], and Instinct maintains a cloud desktop [14]. This is not a chatbot pattern—it is closer to a cloud desktop with an AI occupant. The MVP must build this first.

Truthful, backend-driven state is a trust requirement, not a feature. Muse shows an activity log and permissions under the avatar [13]; Grok Bot uses avatar motion to indicate actual lifecycle state [49]; Cursor exposes a transcript users can read [19]. Fake progress bars or decorative animations that misrepresent actual work destroy trust irreversibly.

Skills over prompts. Cursor's SKILL.md system, Grok Bot's bot routines, and PILOT's reusable skill library [9] all demonstrate that small, tested, versioned skill definitions outperform giant system prompts for reliability, debuggability, and incremental improvement.

Security is architectural, not additive. Muse's Sentinel agent, systemd-nspawn cells, and credential injection [32]; MCP's documented STDIO RCE vulnerability [54]; and Instinct's prompt injection incidents [3] prove that security must be designed into the execution boundary, not bolted on.

The supervisor coordinator-agent pattern is the scalable multi-agent architecture. LangChain benchmarks show swarm slightly outperforms naive supervisor, but a well-implemented supervisor with context isolation outperforms monolithic single agents by 90.2% at scale [24]. Cursor Projects' coordinator-agent pattern [52] and Grok Bot's chief-of-staff pattern [35] both validate this.

What to build first: A single end-to-end vertical slice—one agent, one task category (research), one persistent VM, one verified output—with full observability. This slice proves the architecture before expanding to multi-agent, multi-tool systems.

B. Agent State Machine
The following state machine maps every UI state to a specific backend event. There is no state that exists in UI without a corresponding backend trigger.

States:
  IDLE          ← no active task; heartbeat only
  RECEIVING     ← user message received; parsing intent
  UNDERSTANDING ← model inference: interpreting goal
  PLANNING      ← model inference: generating action plan
  RETRIEVING    ← memory/context lookup in progress
  SELECTING     ← choosing skill/tool
  CHECKING_PERM ← permission gate evaluation
  AWAITING_APPR ← waiting for human approval (amber)
  SEARCHING     ← search API call in flight
  BROWSING      ← Playwright session active
  CODING        ← code generation or terminal execution
  BUILDING      ← creating artifact (doc, file, tool)
  WRITING       ← generating document/report
  ANALYZING     ← data processing / inference on data
  COLLABORATING ← messaging another agent; awaiting subagent
  VERIFYING     ← running verification skill/assertion
  COMPLETED     ← task delivered; outcome verified
  FAILED        ← max retries exceeded or unrecoverable error
  RECOVERING    ← retry logic in progress
State machine transitions (selected critical paths):

IDLE → RECEIVING [event: user_message_received]
  UI: avatar acknowledges (slight lean-forward animation, 150ms)
  
RECEIVING → UNDERSTANDING [event: intent_parse_start]
  UI: status banner "Understanding your request..."
  Timeout: 30s → FAILED with "Could not interpret request"

UNDERSTANDING → PLANNING [event: plan_generation_start]  
  UI: status banner "Building action plan..."
  Activity timeline: shows plan as it streams (not hidden CoT)
  
PLANNING → CHECKING_PERM [event: plan_ready; first_action_selected]
  UI: shows planned steps to user (transparent)
  
CHECKING_PERM → AWAITING_APPR [event: action_requires_approval]
  UI: ApprovalCard surfaced; amber badge on agent; push notification
  Timeout: configurable (default 24h for async tasks, 60s for blocking)
  Timeout action: DENIED → RECOVERING or FAILED per policy
  
CHECKING_PERM → SEARCHING [event: permission_granted; tool=search]
  UI: "Searching [query]..." in activity timeline
  Backend: search API call with attribution
  
BROWSING [event: playwright_session_active]
  UI: BrowserView shows URL + screenshot (Status level by default)
  User can escalate to Preview or Takeover
  Anti-bot/CAPTCHA encountered → AWAITING_APPR for user to solve
  
CODING [event: terminal_command_issued]
  UI: terminal output stream in activity panel (truncated, expandable)
  Sandbox: all terminal commands run in isolated cell, not host
  
VERIFYING [event: verification_skill_invoked]
  UI: "Verifying outcome..." with assertion list
  Backend: runs independent verification (separate model call or deterministic check)
  Success → COMPLETED; Failure → RECOVERING
  
COMPLETED [event: verification_passed; delivery_confirmed]
  UI: green checkmark; artifact pinned in chat; cost summary shown
  Memory: outcome stored if policy allows

FAILED [event: max_retries_exceeded | unrecoverable_error]
  UI: red badge; failure summary (what was tried, what failed, suggested fix)
  No silent failure: user always notified
  
RECOVERING [event: retry_initiated]
  UI: "Retrying with adjusted approach (attempt N/M)..."
  Shows what changed in approach
No fake progress rule: Every timeline entry must correspond to a real backend event with a real timestamp. The UI consumes a server-sent event (SSE) or WebSocket stream of AgentEvent objects. If the backend is silent for more than the configured timeout, the UI surfaces a "waiting" state with elapsed time—not a spinning animation implying activity.

Action summaries vs. chain-of-thought: Users see:

✅ What the agent did: "Searched Google for 'competitor pricing pages' — found 12 results"
✅ What it found: "Extracted pricing from 5 sites; 3 required JavaScript rendering"
✅ What it decided: "Selected Playwright because search API returned insufficient detail"
❌ NOT shown: internal reasoning tokens, self-talk, scratchpad
This mirrors Muse's activity log design [13] and SARSI's design principle of exposing inspectable state rather than private chain-of-thought [50].

PART 4: REAL AGENT LIFECYCLE
A. Lifecycle Specification
goal → interpret/plan → retrieve_context/memory → select_skill/tool →
permission_check → act → observe → evaluate → retry/correct →
independently_verify → deliver
Each step is an explicit state transition with a recorded event. Nothing is implicit.

Step-by-Step Detail
1. Goal Receipt and Interpretation

User submits goal via chat or API
task_created event recorded with task_id, user_id, agent_id, raw_goal, timestamp
Interpretation model call: structured output → InterpretedGoal {objective, constraints, success_criteria, requires_clarification: bool}
If requires_clarification: agent asks question, waits; NOT marked PLANNING
2. Context and Memory Retrieval

Retrieve from: agent's vector store (past task summaries), shared knowledge base, connected service context
SimpleMem-style compression [51]: recent context in full, older context as compressed summary
LangGraph checkpointer loads last checkpoint if task is resumable [38]
3. Plan Generation

Model generates structured plan: list of PlanStep {skill_id, tool_id, input_params, expected_output, approval_required, budget_allocation}
Plan shown to user before execution (transparency)
User can edit plan or approve entire plan
4. Permission Check (per step)

Check against PermissionSet: is this tool allowed for this agent?
Check against ApprovalPolicy: does this specific action require human approval?
High-risk actions (send email, make purchase, delete files, call external APIs with side effects) always require approval [11]
If approval required: emit approval_gate_opened event; surface ApprovalCard; pause execution
5. Execution

Tool call dispatched to appropriate handler (search, browser, terminal, API, file)
Each call is: logged with full input/output, time-bounded (max timeout per tool type), idempotency-keyed to prevent duplicate execution on retry
All terminal commands run in isolated sandbox (systemd-nspawn or Firecracker microVM)
Browser sessions run in isolated Playwright instance with network proxy
6. Observation

Tool output captured as ToolObservation {tool_id, call_id, output, success: bool, duration_ms, tokens_used}
Agent evaluates observation: did it advance toward goal? did it reveal new information requiring plan adjustment?
7. Evaluation and Retry

Model evaluation call: structured output → StepEvaluation {succeeded: bool, reason, adjustment_needed: bool, new_plan_step?: PlanStep}
If adjustment_needed: plan updated, logged, shown to user as "Adjusted approach"
Retry with exponential backoff, max N attempts (configurable per skill)
If max retries: FAILED state surfaced
8. Independent Verification

After task claims completion, a separate verification skill runs
Verification is independent: different model call, different context window
Verification checks: is success criterion met? is evidence present? is output well-formed?
This is not the same model confirming itself—it is a separate structured evaluation
PILOT's research [9] shows that live verification (during execution, not only post-hoc) improves outcomes
9. Delivery

Artifacts pinned to chat; files saved to workspace; verified outcome recorded
task_completed event with: duration, total_tokens, total_cost, verification_result, artifacts_produced
Memory updated per policy: store outcome summary, not full transcript

Approval-gated (soft)	Ask first time; remember choice	Sending email, posting to Slack, writing to shared docs

PART 5: SKILLS AND TOOLS
A. Why Skills Beat Giant Prompts
The key insight from Cursor [19], Grok Bot [17], and the PILOT paper [9] is that large monolithic system prompts degrade in three ways:

Context contamination: A single prompt includes all possible behaviors; the model struggles to separate which rules apply to which task
Undebuggable failures: When a giant prompt produces wrong output, you cannot identify which instruction failed
No versioning: Changing one rule risks breaking others; no rollback path
Token cost: Loading all instructions for every task is expensive; SimpleMem shows 30x token savings from targeted retrieval [51]
Skills are small, single-purpose, versioned, tested modules. The three-tier loading system [44] means:

Tier 1 (~80 tokens/skill): name + description, always loaded for discovery
Tier 2 (~5,000 tokens max): full SKILL.md body, loaded when relevant
Tier 3: reference files, loaded on-demand
Independent analysis estimates 40% token reduction and 15–20% accuracy improvement vs. single-prompt equivalents [44]. (Estimate; low quality source; treat with caution.)

# PART 6: LIVE WEB AND BROWSER ARCHITECTURE

## A. Tool Comparison

| Tool | Mechanism | Strengths | Weaknesses | Best For |
|---|---|---|---|---|
| **Search APIs** (Serper, Brave, Bing) | HTTP API, returns structured results | Fast, cheap, no bot detection | No JavaScript rendering; no interaction | Discovery, link collection |
| **Playwright** | Headless browser automation | Full JS rendering; form fill; screenshots; multi-page | Slow; resource-heavy; bot detection | Forms, dynamic sites, extraction |
| **browser-use** | AI-native browser control | Natural language → browser actions | Less deterministic; newer; less tested | General browsing tasks |
| **Computer-use** | Vision model + mouse/keyboard | Works on any UI including desktop apps | Very slow (~2s/action); expensive; fragile | Desktop apps with no API |
| **MCP browser tools** | MCP server wrapping Playwright | Standardized interface; reusable | MCP STDIO vulnerability [[54]](<https://labs.cloudsecurityalliance.org/research/csa-research-note-mcp-rce-design-vulnerability-20260423-csa/>); requires MCP server | Standardized agentic pipelines |

**Recommendation:** Use Playwright for primary browser automation (most mature, deterministic, excellent evidence retention). Use search APIs for discovery. Use computer-use only when no API or Playwright path exists. Treat MCP as a convenience layer but harden against STDIO vulnerabilities [[54]](<https://labs.cloudsecurityalliance.org/research/csa-research-note-mcp-rce-design-vulnerability-20260423-csa/>).

## B. Browser Agent Architecture (Secure)

User Request ↓ Permission Check (has browser.navigate permission?) ↓ Session Manager → allocate isolated browser session ↓ Network Proxy (authd layer) ├── Blocks: private IP ranges, metadata service (169.254.x.x) ├── Credentials: injected at network boundary (agent never sees raw credentials) [32] ├── Rate limiting: per-domain, per-minute └── Content policy: blocks known malicious domains

↓
Playwright Worker (isolated process/container) ├── Navigate → capture screenshot → emit event ├── Extract → structured data → emit observation ├── Interact → form fill / click → approval gate for side effects └── Download → to workspace directory only

↓
Evidence Retention ├── Screenshot saved to object storage with timestamp ├── Extracted HTML archived (for audit) ├── Source URL, access timestamp, page title recorded └── Evidence linked to task and skill version


## C. Handling Dynamic Pages, Anti-Bot, and Security

**Dynamic pages (JavaScript-heavy):**
- Wait for `networkidle` before extraction
- Use `page.waitForSelector()` with timeout
- Detect SPA routing and wait for content
- If extraction fails: screenshot + retry with different selector strategy

**CAPTCHA and anti-bot:**
- Detect CAPTCHA presence via visual pattern or known selectors
- Surface `AWAITING_APPR` state: user must solve manually (Takeover mode)
- Do NOT use CAPTCHA-solving services (ToS violation, ethical concern)
- After user solves: resume session; session state preserved

**Rate limits:**
- Per-domain rate limiting in proxy (configurable, default: 5 req/min/domain)
- Respect `Retry-After` headers
- Exponential backoff on 429 responses

**Site terms of service:**
- No automated scraping of sites that explicitly prohibit it in ToS
- No scraping of private/authenticated data without explicit user permission
- Robots.txt respected by default; user can override for their own sites

**Prompt injection via web content:**
- Any text extracted from web pages is treated as untrusted data
- Never injected directly into system prompt
- Passed as a structured `web_content` object clearly labeled as external/untrusted
- Model harness marks untrusted sources [[32]](<https://www.eesel.ai/blog/meta-muse-agent>)
- Classifier ensemble outside agent's reach validates extracted content [[32]](<https://www.eesel.ai/blog/meta-muse-agent>)
- Evidence: Muse's Meta CTO describes this exact layered defense [[32]](<https://www.eesel.ai/blog/meta-muse-agent>)

**Credential isolation:**
- Credentials stored in secure vault (never in agent context window)
- Injected at network boundary as surrogate tokens [[32]](<https://www.eesel.ai/blog/meta-muse-agent>)
- Browser session cookie jar isolated per user, per session
- Session terminated and cleaned after task completion

**Success detection:**
- Verification skill checks expected outcome (form submitted, purchase confirmed, data extracted)
- Screenshot comparison: before and after critical action
- HTTP response code monitoring
- Page content assertions: "Order confirmed" text present

# PART 7: MULTI-AGENT SYSTEM AND SCALE

## A. Architecture Pattern Selection

LangChain's benchmarks [[23]](<https://www.langchain.com/blog/benchmarking-multi-agent-architectures>)[[24]](<https://www.langchain.com/blog/choosing-the-right-multi-agent-architecture>) tested three primary patterns:

| Pattern | Performance (τ-bench) | Token Cost | When to Use |
|---|---|---|---|
| **Single agent** | Degrades with distractor domains | Grows with complexity | Single-domain simple tasks |
| **Swarm** | Slightly outperforms supervisor | Lower than supervisor | Known agent roster; same provider |
| **Supervisor** | Good with improvements; +50% with forward_message tool | Higher than swarm | Generic; works with third-party agents; most flexible |

**Recommendation: Supervisor (coordinator-agent) pattern with subagent isolation.** Reasons:
1. Most generic—works with third-party and user-created agents [[24]](<https://www.langchain.com/blog/choosing-the-right-multi-agent-architecture>)
2. Cursor Projects [[52]](<https://cursor.com/blog/projects>) and Grok Bot's chief-of-staff pattern [[17]](<https://x.ai/bot/guides/grok-bot-for-engineering>)[[35]](<https://x.ai/news/introducing-grok-bot>) both validate it at production scale
3. Context isolation (subagents keep their own context windows) prevents token bloat
4. Anthropic's multi-agent system showed 90.2% improvement over single agent using this pattern [[24]](<https://www.langchain.com/blog/choosing-the-right-multi-agent-architecture>)
5. LangGraph Supervisor package provides production-ready implementation [[23]](<https://www.langchain.com/blog/benchmarking-multi-agent-architectures>)

The key improvement from naive supervisor: **do not require supervisor to translate subagent responses to user**—use `forward_message` tool to pass responses directly [[23]](<https://www.langchain.com/blog/benchmarking-multi-agent-architectures>).

PART 8: AGENTIC ENGINEERING
A. Engineering Agent vs. Code Generator
This distinction is fundamental and is central to Cursor's value proposition [18][19]:

Code Generator	Engineering Agent
Produces code from prompt	Understands existing architecture
No awareness of codebase	Maps dependencies, imports, patterns
No verification	Runs tests, reads logs, verifies outcome
Single-shot	Iterates: plan → build → test → debug → re-test
No CI integration	Reads CI results, responds to failures
No PR process	Opens PR with description, handles review

B. Engineering Agent Workflow in an Existing Repo
Phase 1: Codebase Ingestion
1. Clone repo → git clone {repo_url} --branch {branch}
2. Generate codebase map:
   - File tree with sizes and types
   - Dependency graph (import analysis)
   - Key entry points (main, index, routes)
   - Test coverage map
   - Linter configuration (eslint, ruff, etc.)
   - CI/CD pipeline definition (.github/workflows, etc.)
3. Store codebase map in agent memory (vector store + structured summary)
4. Load codebase-specific skills from .cursor/rules/ and SKILL.md files [[19]](<https://cursor.com/blog/agent-best-practices>)
Phase 2: Task Planning
1. User submits: "Add rate limiting to the API endpoints"
2. Agent uses /code-architect skill:
   - Reads relevant files (route handlers, middleware, auth)
   - Identifies: what exists, what's needed, what might break
   - Generates implementation plan with file paths and line references
3. Plan shown to user before any code written [[19]](<https://cursor.com/blog/agent-best-practices>) (Plan Mode equivalent)
4. User approves or edits plan
Phase 3: TDD Implementation
1. Write failing tests first (/tdd-workflow skill):
   - Identify test file location convention
   - Write tests that define desired behavior
   - Run tests: confirm they fail (red)
   
2. Implement code to pass tests:
   - Small, targeted changes
   - One logical unit per change
   - Reference existing code patterns from codebase map
   
3. Run tests: confirm they pass (green)
4. Run linter: confirm no new violations
5. Commit to feature branch
Phase 4: Verification
1. /code-review skill:
   - Read diff
   - Check against codebase patterns
   - Security review: injection risks, auth bypass, data exposure
   - Performance: N+1 queries, missing indexes, unbounded loops
   
2. If issues found:
   - List issues with severity
   - Fix critical issues before PR
   - Note non-critical for PR description
   
3. Run full test suite (not just new tests)
4. Check for regression in related tests
Phase 5: PR and CI
1. Open PR:
   - Description: what changed, why, how tested
   - Screenshots (for UI changes)
   - Link to original task
   
2. Wait for CI:
   - Read CI logs on failure
   - Debug with /debug-hypothesis skill
   - Push fix commit
   
3. Respond to review comments:
   - Parse review feedback
   - Implement requested changes
   - Re-request review
   
4. On approval: notify user for merge decision
   (Auto-merge only for high-confidence, low-blast-radius changes [[17]](<https://x.ai/bot/guides/grok-bot-for-engineering>))

PART 9: SELF-IMPROVEMENT RESEARCH
A. Memory Survey Framework
The survey "Memory in the Age of AI Agents" [6] identifies three dominant memory forms:

Token-level: In-context; ephemeral; lost after session
Parametric: Baked into model weights; requires fine-tuning to update
Latent: Intermediate representations; model-specific
And a functional taxonomy distinguishing:

Factual memory: Stored facts about the world and user
Experiential memory: Past task outcomes, successes, failures
Working memory: Active task context
This taxonomy directly informs the platform's memory architecture: Redis for working memory, pgvector for factual/experiential, model weights updated only via the safe improvement pipeline.

B. Key Papers
Reflexion (Shinn et al., 2023)
arXiv: [28] arxiv.org/abs/2303.11366

Method: Agents verbally reflect on task feedback signals (scalar or natural language) and store reflective text in an episodic memory buffer. No weight updates. The reflection becomes a lesson that informs the next trial.

Evidence: 91% pass@1 on HumanEval coding benchmark, surpassing GPT-4's 80% [28]. Improvements across sequential decision-making, coding, and language reasoning.

Limits: Requires multiple trials (expensive). Reflections can be wrong (self-evaluation unreliable per [50]). Memory buffer has finite capacity. Does not update weights.

Implementable lesson: After a failed task, have the agent generate a structured reflection: {what_was_tried, what_failed, why_it_failed, what_to_try_next}. Store in episodic memory, retrieved at start of next similar task. This is the foundation of the platform's failure learning system.

PILOT: Live Self-Improvement for Long-Horizon Agents (Xiao et al., 2026)
arXiv: [9][29] arxiv.org/abs/2608.26530 (submitted 27 Aug 2026)

Method: Supervisor-worker harness with two mechanisms: (1) live steering—supervisor redirects active worker during execution via a live channel (notification, question, steer, abort); (2) live self-evolution—procedures and failure modes distilled into reusable skills and memory during execution, not only after.

Evidence: 71.6% average on Terminal-Bench 2.0 vs. 66.3% baseline (+5.3pp) [9]. Self-improvement gains of 14.6pp (GLM-5.1) and 12.4pp (Kimi-K2.6) across iterations. Skill library grows from ~50-62 to ~81-83 skills. Token consumption falls 42-47%. Cost-efficiency (successful evals/million tokens) rises 110-134% [9].

Limits: Expensive to iterate (runs all tasks across iterations). Supervisor and worker share the same backbone (limits independence). Only studied two backbones. Long-horizon task pass rate still below 80% even after improvement.

Implementable lesson: Implement a supervisor process that monitors running agent tasks and can inject steering signals. Distill successful task patterns into new skill candidates. Evaluate candidates on held-out tasks before deploying.

SelfMem: Self-Optimizing Memory for AI Agents (2026)
arXiv: [30][39] arxiv.org/abs/2607.03726

Method: Agent controls its own memory management via memory tools and feedback signals. It explores, evaluates, and refines its memory strategy rather than using a fixed pipeline.

Evidence: 48.7%, 40.8%, 41.9% improvement over strongest baseline at 100K, 500K, 1M token scales on BEAM benchmark [30]. At 1M tokens: SelfMem score 0.454 at $2.004 vs. Mem0 score 0.292 at $18.830 [39]. Simple RAG remains the strongest non-SelfMem baseline.

Limits: Results are self-reported on a single benchmark (BEAM). Iterative refinement study only at 100K scale. No production deployment evidence.

Implementable lesson: Start with RAG (it's the strongest baseline and simplest to implement). Allow agents to annotate their own memories as useful/not-useful based on task outcome. Periodically prune low-quality memories. This is SelfMem-light without the full framework complexity.

SimpleMem: Efficient Lifelong Memory (2026)
arXiv: [51] arxiv.org/html/2601.02553v1

Method: Three-stage pipeline: Semantic Structured Compression → Recursive Memory Consolidation → Adaptive Query-Aware Retrieval. Uses LanceDB with text-embedding-3-small for dense, BM25 for sparse, SQL for metadata.

Evidence: 26.4% average F1 improvement on LoCoMo benchmark. 30x token reduction vs. full-context approaches (531 tokens/query vs. 16,900) [51]. GPT-4.1-mini: 43.24 F1 vs. 34.20 for Mem0.

Implementable lesson: Use hybrid indexing (dense + sparse + metadata). Compress older memories rather than truncating. Retrieval depth of 3-20 entries is sufficient (most value from top few). LanceDB is open source and practical.

SARSI: Self-Aware Recursively Self-Improving Agents (2026)
arXiv: [50] arxiv.org/html/2607.12254v2

Method (position paper): Proposes agents with persistent machine-readable self-models covering identity, capabilities, limitations, uncertainty, and development history. Improvement proposals require: evidence linkage, human approval through owner gateway, test on held-out tasks, gradual rollout.

Evidence: Theoretical/design paper; no empirical results. Authors explicitly state this is not evidence that recursive self-improvement has been achieved [50].

Key governance principle: "A mode change that expands authority is approved through the owner gateway, not by the model itself" [50]. The governance plane runs under a different administrative identity and, for high-risk systems, a separate host [50].

Implementable lesson: Self-improvement proposals are versioned, tested against baseline, reviewed by a human, and rolled out incrementally. The agent cannot modify its own permission policies, audit trail, or improvement governance.

C. Self-Improvement vs. Other Adaptation Types
Type	Mechanism	Speed	Reversibility	Evidence Required
In-context reflection	Linguistic reflection in context	Immediate	Session-scoped	None (per Reflexion)
Episodic memory	Store outcomes; retrieve at task start	Per task	Deletable	Task outcome
Skill update	Revise SKILL.md content	Hours	Full rollback	Held-out test suite
Prompt/rule update	Revise system prompt or .cursor/rules	Hours	Full rollback	Eval benchmark
Policy learning	RL fine-tuning on outcome signals	Days	Requires rollback	Large dataset + eval
Weight update	Fine-tune foundation model	Days-weeks	Requires rollback + audit	Extensive eval suite
Safe improvement pipeline (proposed, not vendor-claimed):

1. Collect: task outcomes with metadata (skill_version, model, success/fail, cost)
2. Evaluate: identify patterns of failure (e.g., /web-research fails on paywalled sites)
3. Propose: generate versioned skill update candidate (human-readable diff)
4. Test: run candidate on held-out task set; must beat baseline by ≥5%
5. Review: human approves the change and the test methodology
6. Stage: deploy to 5% of tasks; monitor failure rate for 48h
7. Promote: if stable, promote to full rollout; otherwise rollback to prior version
8. Audit: all changes logged with who approved, what tests passed, what changed
PART 10: REAL BUSINESS VALUE
A. Evidence-Graded Use Cases
1. Software Development / Engineering Productivity
Evidence (strongest available):

Goldman Sachs deployed Devin as "Employee #1" in a hybrid workforce (reported, July 2026, IBM/CNBC) [45]. CIO Marco Argenti framed it as a 20% productivity multiplier scenario: 12,000 engineers operating like 14,400 [45]. Note: this is an illustrative scenario, not a measured ROI claim.
Cursor Projects reports: new users merge 30% more PRs; users who primarily use Projects merge 6x as many PRs [52]. These are vendor-reported; treat as vendor-claimed.
A Grok Bot author reports shipping 2,000+ PRs in a month and building Grok Bot iOS v0 in three weeks [17]. User-reported; not independently verified.
LinearB data (8.1M PRs from 4,800 teams): AI PRs merge within 30 days only 32.7% of the time vs. 84.4% for unassisted PRs [53]. This is the counter-evidence: human review is a bottleneck for AI-generated code. Agentic AI PRs wait 17.6 hours at 75th percentile for pickup vs. 3.4 hours for unassisted [53].
Median PR throughput gain across 400+ organizations over 14 months: 7.76% [46]. Elite teams: 5-15% [46]. These figures are from a low-quality source citing DX benchmarks; treat as rough estimates.
Critical observation: The software delivery bottleneck shifted to review and release, not generation [53]. The platform must address review quality and throughput, not just code generation speed.

Verification approach: Track PR acceptance rate (AI vs. unassisted), merge time, rework rate, test coverage delta, defect escape rate [53][46].

KPI targets (realistic, not vendor-inflated):

PR throughput: +10-30% (achievable; not the 3-10x vendor claims)
Review cycle time: measurable only if agents also assist review
Regression rate: should not increase vs. baseline

Muse can negotiate on a user's behalf after researching options [12]. These are vendor-claimed capabilities; no independent ROI figures.

Realistic agent workflow:

60-90 minutes of human research → 5-10 minutes agent research + 15 minutes human review
Bottleneck becomes: quality of sources, paywall access, structured output format
Verification: Cross-reference agent-found pricing/feature claims with at least one additional source. Record source URLs, access timestamps. Human reviews final report.

KPI: Research task completion time (hours → minutes); source count and citation rate; human correction rate per report.

3. Lead Research / Sales Development
Evidence: Grok Bot's internal use: "a sales Bot updating the CRM with call transcript notes and drafting follow-ups" [35]. Grok Bot marketplace has pipeline generation bots that research accounts, score contacts, draft email and LinkedIn in the user's voice, and surface a review list [16]. These are vendor-described internal uses, not independently verified customer deployments.

Caution on LinkedIn: Automated scraping of LinkedIn violates their ToS (hiQ Labs v. LinkedIn). Use only official LinkedIn APIs or user-initiated data exports.

Realistic value: Agent can research company publicly available information (website, press releases, job postings, product pages, reviews) and draft personalized outreach. Human reviews and approves before sending.

KPI: Accounts researched per hour; outreach personalization score; reply rate (requires A/B with human-drafted baseline).

4. Data Analysis
Evidence: Devin "sets up the code environment, reproduces bugs, and codes and tests fixes on its own" [45]. For data analysis specifically, no independently verified case study with numbers was found in the evidence set. The Python sandbox capability is confirmed for code execution [19][22].

Realistic workflow: Upload CSV → agent writes Python (pandas/matplotlib) → runs in sandbox → returns charts + summary → human reviews interpretation. Time savings: analysis setup time reduced; interpretation still requires human judgment.

KPI: Analysis task time; chart accuracy vs. manual; human corrections per analysis.

5. Customer Operations / Workflow Automation
Evidence: Instinct reported 677 messages in 5 days and 15 completed jobs per early user [3]. Tasks included bill negotiation, vendor coordination, ticket monitoring, subscription audits [3]. These are user-reported (low quality source), not independently audited.

Instinct sent an email without confirmation (Katie Jacobs Stanton incident [33]). Instinct was prompt-injected via a test email [3]. These are documented production failures.

Key risk: Autonomous customer-facing actions without approval gates create legal and reputational exposure. The Instinct failures demonstrate the cost of insufficient HITL.

Requirement for production deployment: Every customer-facing action (email, Slack message, form submission, purchase) must be approval-gated. Autonomous action only for purely internal read operations.

PART 13: SECURITY, RELIABILITY, AND COMPLIANCE
A. MCP Security: Critical Vulnerabilities
On April 15, 2026, OX Security disclosed a critical STDIO transport vulnerability in Anthropic's MCP SDKs (Python, TypeScript, Java, Rust): user-controlled configuration values are passed directly to shell execution without sanitization [54]. The command executes even when the target process fails to start. Anthropic characterized this as "expected" behavior [54].

Scale: Over 150M package downloads, ~7,000 publicly reachable servers, ~200,000 vulnerable deployments, 14+ CVEs [54].

Tool poisoning: MCP tool descriptions are visible to the AI model but hidden from human users. An attacker who controls a tool description can embed hidden instructions the model reads and acts upon without user knowledge [54].

Mitigations required for this platform:

Never use MCP STDIO transport in production. Use HTTP/SSE transport only.
Validate all MCP tool descriptions at initialization against a known-good baseline. Alert on unexpected changes [54].
Process isolation: Run each MCP server in its own container or microVM.
Command allowlisting: If any shell execution is required, use an explicit allowlist of hardcoded binary paths.
Content validation: All tool description text validated against injection patterns before loading.
B. Prompt Injection Mitigations (2026 State)
Muse's CTO describes a layered defense [32]:

Model training: Model trained to recognize and resist injection
Harness marking: All content from untrusted sources explicitly labeled
Deterministic code checks: Result of agent action checked by deterministic code, not another model call
Classifier ensemble: Runs outside agent's reach (separate process, separate context)
Additional mitigations:

Web content always passed as a clearly labeled {source: "untrusted_web", content: "..."} structure, never interpolated into system prompt
Output validation: any agent output that will be sent externally (email, API call) validated against injection patterns
Simon Willison's "lethal trifecta" [32]: private data + untrusted web content + outbound communication capability together create prompt injection risk. Defense requires: Sentinel-pattern approval for all outbound, credential isolation, and content labeling.
C. Multi-Tenancy and RBAC
Tenant (Organization)
  └── Users
        └── Agents (agent_id + user_id + org_id)
              └── Tasks
                    └── Tool grants (scoped to task)

RBAC roles:
  - Owner: full control including billing, agent creation, skill publishing
  - Admin: create/edit/delete agents; set approval policies; view all tasks
  - Member: create/run own agents; view own tasks
  - Viewer: view task history and outputs only

Row-level security (PostgreSQL RLS):
  - All queries automatically filtered by user_id + org_id
  - Agents can only access their own workspace directory
  - Cross-agent resource access only via explicit delegation records
D. Secret Management
Credentials stored in vault (HashiCorp Vault or AWS Secrets Manager)
Injected at network boundary as surrogate tokens (agent never sees raw credential)
Short-lived task-scoped credentials where possible
Rotation policy: all credentials rotated every 30 days
Audit log: every credential access recorded with timestamp, agent_id, tool_id
E. Sandbox and Browser Isolation
Resource	Isolation Method	Evidence
Code execution	E2B Firecracker microVM (dedicated kernel) [22]	Hardware-level isolation
Browser	Playwright in isolated process + network proxy	Per-session; cleaned after task
Private IP blocking	E2B blocks link-local and metadata IPs [22]	Prevents SSRF attacks
Credential injection	Network proxy layer; never in agent context	Muse architecture [32]; E2B model [22]
Agent workspace	Per-agent directory in user VM	No cross-agent file access
F. Reliability Patterns
Idempotency: Every tool call carries an `idempotency_key = f"{task_id}-{step_index}". Duplicate execution on retry is detected and skipped.

Timeouts: Every tool call has a hard timeout. Every agent run has a task-level budget (tokens + cost + time). Exceeded budgets surface a FAILED state with clear explanation.

Retries: Exponential backoff with jitter. Max 3 retries for transient failures. No retry for authorization failures or budget exceeded.

Resumability: LangGraph checkpointer saves state after each step [38][41]. If the worker process dies, the task resumes from last checkpoint on restart.

Runaway loop detection: Maximum step count per task (configurable, default 50). Maximum token budget per task. Temporal workflow has maximum execution time. Any of these exceeded → FAILED with explanation.

Backup and rollback: PostgreSQL point-in-time recovery. Skill versions never deleted (deprecated, not deleted). Agent state checkpoints retained for 30 days. Temporal provides full workflow execution history [47].

from langgraph.checkpoint.postgres import PostgresSaver

class ResearchAgentState(BaseModel):

    goal: str

    artifacts: list[str] = []

    token_count: int = 0
    cost_usd: float = 0.0

def build_research_agent_graph(
    agent_config: AgentConfig,
    checkpointer: PostgresSaver
) -> StateGraph:
    
    graph = StateGraph(ResearchAgentState)
    
    # Nodes map to lifecycle states
    graph.add_node("interpret", interpret_goal_node)
    graph.add_node("retrieve_context", retrieve_context_node)
    graph.add_node("plan", plan_node)
    graph.add_node("check_permission", check_permission_node)
    graph.add_node("execute_tool", execute_tool_node)
    graph.add_node("evaluate", evaluate_step_node)
    graph.add_node("verify", verify_completion_node)
    graph.add_node("deliver", deliver_node)
    graph.add_node("handle_failure", failure_node)
    
    # Edges define legal transitions
    graph.add_edge(START, "interpret")
    graph.add_edge("interpret", "retrieve_context")
    graph.add_edge("retrieve_context", "plan")
    graph.add_edge("plan", "check_permission")
    
    graph.add_conditional_edges(
        "check_permission",
        route_after_permission_check,
        {
            "approved": "execute_tool",
            "needs_approval": "check_permission",  # wait state in Temporal
            "denied": "handle_failure"
        }
    )
    
    graph.add_conditional_edges(
        "evaluate",
        route_after_evaluation,
        {
            "continue": "check_permission",  # next step
            "verify": "verify",
            "retry": "execute_tool",
            "failed": "handle_failure"
        }
    )
    
    graph.add_edge("execute_tool", "evaluate")
    graph.add_conditional_edges(
        "verify",
        route_after_verification,
        {
            "passed": "deliver",
            "failed": "execute_tool"  # retry with adjusted approach
        }
    )
    graph.add_edge("deliver", END)
    graph.add_edge("handle_failure", END)
    
    return graph.compile(checkpointer=checkpointer)

# FINAL RECOMMENDATION: WHAT TO BUILD FIRST AND WHY

## The Vertical Slice: Research Agent with Truthful Activity Stream

**Build this first:** A single Research Agent that accepts a goal, executes a search-browse-extract-verify-report workflow, streams real backend events to the UI, surfaces an approval gate before any external action, and delivers a cited artifact.

**Why this specific slice:**

1. **It proves the hardest architectural problems:** truthful state machine, SSE event streaming, permission gates, evidence retention, and independent verification—all in one flow.

2. **It has immediate measurable value:** A research task that saves 45 minutes of human work and delivers a sourced report is demonstrably useful on day one.

3. **It validates the security model:** Browser isolation, credential injection, content labeling, and output verification are all exercised by a research task.

4. **It creates the evaluation baseline:** You can measure whether the research is accurate, sourced, and complete. This baseline is needed before any skill improvement work.

**Objective proof it works:**
- Run 10 research tasks on known-answer questions (e.g., "What is Anthropic's current pricing for Claude Pro?")
- Measure: all 10 return the correct answer with a valid source URL
- Measure: all 10 show truthful activity timelines (each event has a real timestamp and real tool call)
- Measure: zero hallucinated URLs (check each citation is accessible)
- Measure: cost per task < $0.50
- Measure: task completion time < 3 minutes

If this succeeds, every subsequent agent role, skill, and feature has a proven infrastructure to build on. If it fails, you discover the failure mode on the simplest possible scenario before committing to multi-agent complexity.

**The platforms reviewed—Muse [[12]](<https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/>), Instinct [[14]](<https://instinct.com/>), Grok Bot [[16]](<https://x.ai/bot>)[[17]](<https://x.ai/bot/guides/grok-bot-for-engineering>), and Cursor [[19]](<https://cursor.com/blog/agent-best-practices>)[[52]](<https://cursor.com/blog/projects>)—all started from a single, well-defined use case and expanded from there.** The mistake is starting with the marketplace, the orchestration layer, and the multi-agent patterns before proving that one agent can reliably complete one real task.
